# 명조 설치본 분석

이 폴더에 명조 전용 도구와 테스트가 있습니다. 중부 평원 무음구역의 재화 분석과 개선안은 한 개의 HTML로 열 수 있습니다. [단일 보고서](개별보고서/명조_중부평원_무음구역/중부평원_무음구역_재화분석과_개선안.html)

이 프로젝트에는 명조의 변형된 **Unreal PAK v12**를 읽는 전용 어댑터가 있다. 3.8.0 Windows 설치본에서 PAK → SQLite DB → 클라이언트 FlatBuffers 정의 → 보상·성장 계산까지 실행했다. 게임 프로세스나 설치 파일을 수정하지 않는다.

현재 결과는 `콘텐츠/명조/클라이언트분석/설계결과.json`에 연결되어 있다. 주 분석 범위는 **중부 평원 무음구역과 5성 에코 성장**, 비교 범위는 캐릭터·무기의 클램 코인 소비다. 보고서의 `analyzed_partial`은 확인한 범위의 정적 분석은 끝났지만 실제 지급 분포·부옵션 확률·성장 기간까지 검증한 상태는 아니라는 뜻이다.

## 구성과 의존성

| 도구 | 역할 | 의존성 |
| --- | --- | --- |
| `도구/명조_클라이언트.py scan` | 설치 경로의 Unreal PAK 버전·색인 정보 조사 | Python 3.10+ |
| `list`, `extract` | v12 색인 해석·부분 AES 복호화·선택 추출 | 암호화 파일은 Python `cryptography`; Oodle 파일은 호환 로컬 라이브러리 |
| `snapshot` | SQLite 키 열과 BinData를 중간 JSON으로 저장 | Python 표준 라이브러리 |
| `도구/명조_DB해석.cjs` | 같은 설치본의 생성된 schema getter로 해석, SQLite 키와 대조 | Node.js; npm 패키지 불필요 |
| `report` | 원본·해석 테이블 해시 검증, 비용·환급 계산, CSV/JSON/HTML | Python 표준 라이브러리 |

공통 프로젝트의 `도구/밸런스.py` 모델 계산기는 계속 Python 표준 라이브러리만 사용한다. 명조 추출 키는 AI API 키가 아니다. 키·추출 DB·코드·압축 라이브러리는 Git에서 제외한 로컬 분석 회차에 둔다.

현재 어댑터는 v12 전체 디렉터리 색인, 인코딩된 엔트리, 무압축·Zlib 및 외부 Oodle 디코더, 명조 부분 암호화 모드 0/1/2/4를 지원한다. 다른 PAK 버전·비인코딩 엔트리는 명시적 오류로 중단한다. 일반 Unreal/Unity 추출기로 취급하지 않는다.

## 재실행 흐름

Codex에는 아래처럼 요청한다.

```text
명조 설치본을 다시 분석해줘. C:\Program Files\Wuthering Waves에 있어.
기존 추출 회차를 보존하고 새 회차에서 무음구역 보상과 에코 성장 비용을 비교해줘.
서버 지급량을 확인하지 못했으면 파밍 일수는 미확인으로 남겨줘.
```

직접 실행할 때는 새 출력 경로를 사용한다. 다음은 이 문서가 있는 게임별 작업 폴더 기준 예다. `추출회차`는 사용자가 정한 새 폴더이며 기존 결과와 겹치면 안 된다.

```bash
python3 도구/명조_클라이언트.py --help
python3 도구/명조_클라이언트.py scan --source 'C:\Program Files\Wuthering Waves' --out '추출회차/패키지목록.json'
python3 도구/명조_클라이언트.py list --pak '/원본/pakchunk44-WindowsNoEditor.pak' --key-map '로컬_키매핑.json' --match 'ConfigDB' --out '추출회차/DB목록.json'
python3 도구/명조_클라이언트.py extract --pak '/원본/pakchunk44-WindowsNoEditor.pak' --key-map '로컬_키매핑.json' --match 'db_(phantom|role_level)\.db$' --out '추출회차/DB원본'
python3 도구/명조_클라이언트.py snapshot --db-root '추출회차/원본추출/Client/Content/Aki/ConfigDB' --out '추출회차/DB_중간입력.json'
node 도구/명조_DB해석.cjs '추출회차/원본추출/Client/Content/Aki/JavaScript' '추출회차/DB_중간입력.json' '추출회차/테이블'
```

`--key-map`은 `{ "Client/Content/Paks/파일명.pak": "64자리 hex" }` 형태의 로컬 JSON이다. 추출 대상 PAK에 맞는 키를 확인한 뒤 사용한다. 색인·디렉터리 SHA-1이 일치해야 해석한다. Oodle 엔트리는 `--oodle-lib <로컬 라이브러리>`를 추가한다. 라이브러리와 키를 자동 다운로드하지 않는다.

위 최소 예는 모든 보고서 입력을 준비하는 명령 묶음이 아니다. 보고서는 `Phantom*`, `Role*`, `Weapon*`, `ExchangeReward`, `DropPackage`, `SilentAreaDetection`, `ItemInfo`와 한국어 `MultiText`, `CommonParam` 및 관련 클라이언트 코드를 요구한다. 실제 3.8.0 회차의 `추출_명세.json`에 선택한 전체 파일과 원본 패키지·엔트리·오프셋·해시가 있다. 여러 패키지의 결과를 한 원본추출 트리에 모을 때 경로 충돌을 확인하고 추출 명세를 병합한다.

현재 완료된 추출본으로 보고서만 다시 계산하려면:

```bash
python3 도구/명조_클라이언트.py report \
  --tables '콘텐츠/명조/클라이언트분석/추출/20261118_클라이언트/테이블_3' \
  --extracted '콘텐츠/명조/클라이언트분석/추출/20261118_클라이언트/원본추출/Client/Content/Aki' \
  --manifest '콘텐츠/명조/클라이언트분석/추출/20261118_클라이언트/추출_명세.json' \
  --out '콘텐츠/명조/클라이언트분석/결과/새_분석회차'
```

## 수치를 해석할 때

- `DropPreview`는 지급 테이블이 아니다. 0 수량을 실제 0이나 확률로 바꾸지 않는다.
- 에코는 목표 레벨까지의 `PhantomLevel.Exp`를 합한다. 캐릭터는 `RoleLevelData`에 따라 다음 레벨 행, 무기는 `WeaponDataBase`에 따라 현재 레벨 행을 읽는다. 동일한 행 범위를 쓰면 한 레벨 차이가 난다.
- `CommonParam`의 Int 값이 항상 4바이트 BLOB인 것은 아니다. 클라이언트 `DeserializeConfig.ParseInt`처럼 앞 4바이트만 읽고, 소비 코드의 `/1000` 등 단위를 적용한다.
- 콘텐츠 연결은 직접 ID 참조인지 동일 보상맵에 따른 추론인지 기록한다. 미리보기·설치본 데이터가 서버의 현재 지급과 같다고 보장하지 않는다.
- `파밍설계_입력.json`의 미확인 지급량·합격률은 null이다. 실제 로그/지급 데이터로 채운 뒤 별도 기간 모델을 만든다. 이 파일은 `밸런스.py simulate`의 입력 형식이 아니다.

## 지급량·확률 추가 조사

2026-11-18 추가 조사는 `콘텐츠/명조/클라이언트분석/추출/20261118_확률추적/`에 있다. 83개 PAK의 색인과 1,579,538개 엔트리, JavaScript 20,996개를 조사했다. `aki_base.csv`의 1,878개 테이블 등록 정보와 관련 DB도 대조했다. 전체 에셋의 내용이나 모든 테이블 행을 해석한 범위는 아니다.

- `ItemHintController`는 메시지 22096을 받아 `OnItemRewardNotify`를 전달하고, `ItemRewardController`는 응답의 아이템 ID·수량을 읽는다. 별도 아이템 획득 알림 18089도 서버가 보낸 수량을 사용한다.
- `PhantomBattleController.RequestPhantomIdentify`는 26204 요청 후 응답의 `xPs`를 적용한다. `PhantomDataBase.UpdateData`는 `Wws`를 부옵션 목록으로 받는다. 이 경로에서 실제 결과는 서버 응답에 있다.
- `DropPackage`의 `DropPreview`와 `PhantomSubProperty`의 속성 정의에는 해당 콘텐츠의 지급·추첨 가중치가 없다. `PhantomPropRandom`은 `PhantomItem.MainProp`에 쓰이는 그룹 참조다. 이름만 보고 부옵션 확률표로 간주하지 않는다.
- 원시 `dropunit`·`phantomsubpropaction` 테이블과 `PhantomCritRateDic` 키는 발견했지만, 검색한 JavaScript에서 해당 이름의 사용처를 확인하지 못했다. 오래된 데이터인지·네이티브 코드에서 쓰는지는 단정하지 않는다. 원시 정수를 현재 확률로 해석하지 않는다.

`설계결과.json`의 `probability_investigation`에 당시의 근거 보고서·입력 해시·검토 경로가 있다. 설치본에서 못 찾은 분포는 공식 확률 공개와 실제 지급·튜닝 관측으로 보완할 수 있다. 보상은 같은 회차의 전체 지급 묶음·난이도·배수를, 튜닝은 성공품만이 아닌 모든 시도·이전 부옵션·슬롯·실제 수치를 기록한다. 평균 보상량과 옵션 개수만으로 p50/p90 파밍 기간을 만들지 않는다.

## 공개 자료를 연결한 콘텐츠별 기획

사용자가 공개 실측 자료 활용을 허용한 2026-11-18 회차는 `결과/20261118_콘텐츠기획/`에 있습니다. 로컬 회차의 `보고서/명조_콘텐츠별_보상밸런스_기획서.html`과 Markdown을 함께 생성합니다. 이전에 미확인으로 기록했던 부옵션 분포는 [공식 한국어 확률 공시](https://sdk-prod-cdn-aws.kurogame-service.com/pro/agreement/common/language_ko/product_info.pdf)로 보완했습니다. 서버 내부 테이블을 추출한 것은 아닙니다.

- `외부자료/20261118/`: 원본 공식 PDF, 공개 실측 XLSX, 수집 URL·SHA-256, 정규화한 확률·관측·요약. 채택 관측은 7,614건이며 2.0~2.5와 버전 미기재 자료입니다. 3.8 현행 지급 분포를 검증한 것으로 취급하지 않습니다.
- `추출/20261118_콘텐츠기획/테이블_등록부/`: `aki_base.csv`의 현재 DB 매핑과 일치하는 추가 173개 테이블, 14,847행. 같은 이름의 오래된 테이블을 다른 DB에서 해석하면 최신 스키마와 어긋날 수 있습니다. 초기 부분 결과 `테이블/` 대신 이 폴더를 사용합니다.
- `입장비_연결근거.json`: 가이드 → 입구 → 실제 인스턴스 → `InstanceDungeon.RewardId` → `ExchangeReward.Cost`의 소비 코드 근거입니다. `RewardId`를 곧바로 DropPackage ID로 읽지 않습니다. 입구의 `PowerCostShow`에는 실제 비용과 다른 값이 있어 비용 근거로 사용하지 않습니다.
- `결과/20261118_콘텐츠기획/콘텐츠_근거.json`: 209개 가이드, 시즌/난이도 보상 프로필, 392개 Activity 등록 행. 등록은 현재 활성 상태를 뜻하지 않습니다.
- `파밍_입력.json`: 일반 밸런스 엔진과 다른 `wuwa_conditional_farming_v1` 형식입니다. 공식 13종 비복원 확률, 단계별 비용·환급, 실제 관측 보상 묶음, 선별 정책을 담습니다.

```bash
python3 도구/명조_파밍계산.py \
  --input '콘텐츠/명조/클라이언트분석/결과/20261118_콘텐츠기획/파밍_입력.json' \
  --out '콘텐츠/명조/클라이언트분석/결과/새_파밍검증'

python3 도구/명조_기획서.py \
  --run '콘텐츠/명조/클라이언트분석/결과/20261118_콘텐츠기획' \
  --sources '콘텐츠/명조/클라이언트분석/외부자료/20261118' \
  --out '콘텐츠/명조/클라이언트분석/결과/새_기획서'
```

출력은 새 폴더여야 합니다. 입력이 참조한 원본 해시가 다르면 재사용하지 않습니다. 재화 파밍은 유효 세트·주옵션 후보가 충분한 조건이며 실제 후보 획득·해금·전투 시간을 계산하지 않습니다. 초기 재고 0, EXP/튜너 부족 시 무음구역, 코인만 부족하면 코인 영역을 즉시 수령하는 정책입니다. 최소 행동력 최적화가 아닙니다. 코인 84,000과 튜너 20은 시트 작성자의 고정 기재값이며 개별 지급 관측으로 검증한 분포와 구분합니다.

20개 유형별 기획서의 변경안은 실제 서버에 적용하지 않습니다. 주기 보상 재분배는 프로필별 예산을 보존하며 공유 Drop ID를 수정해 다른 시즌까지 바꾸지 않도록 새 보상 ID 연결을 검토합니다. 최신 `설계결과.json`은 과거 설치본 분석과 공개 자료 보완, 조건부 계산, 제안 검토를 별도로 기록합니다.

## 기획서·분석서·제안서 모음

로컬 생성본은 `문서/명조/index.html`에서 엽니다. `기획서/`, `분석서/`, `제안서/`에 본문을 목적별로 작성하고 각 문서의 HTML과 Markdown을 함께 둡니다. 이 폴더의 문서 첫 화면에서도 세 모음으로 갈 수 있습니다. [명조 문서 첫 화면](index.html)

추가 검토 회차 `결과/20261118_문서체계화/`에는 튜너 20·22·24·26개와 EXP 10% 증가 대안을 동일한 5,000개 시드로 비교한 입력·결과·시행 CSV가 있습니다. 평균 차이는 쌍체로 비교하고 p90에는 DKW 기반 모의 오차 구간을 붙였습니다. 이 구간은 실제 서버값의 불확실성을 모두 포함하지 않습니다. 추가 목표는 기획자 제안 기준으로, 사용자 확정 조건이나 실제 서비스 성과로 취급하지 않습니다.

```bash
python3 도구/명조_검토계산.py \
  --input '콘텐츠/명조/클라이언트분석/결과/20261118_문서체계화/민감도_입력.json' \
  --out '콘텐츠/명조/클라이언트분석/결과/새_대안검증'
```

## 명조 조건부 파밍 입력

`도구/명조_파밍계산.py`는 위 일반 모델과 다른 `wuwa_conditional_farming_v1` 형식을 받습니다. 실제 예시는 `콘텐츠/명조/클라이언트분석/결과/20261118_콘텐츠기획/파밍_입력.json`입니다.

- `source_files`: 입력 근거 파일의 절대 경로와 SHA-256. 실행 전에 일치 여부를 검사합니다.
- `disclosure`: 공식 공개 부옵션 13종, 수치별 확률. 공개 반올림 합계는 정규화합니다.
- `checkpoints`: +5/+10/+15/+20/+25의 누적 EXP, 코인, 폐기 환급량.
- `tacet_rows`: 같은 수령에서 함께 관측된 EXP와 코인 묶음. 묶음 단위로 복원 추출합니다.
- `echo_scenarios`: 목표 종류·최저 수치, 선별 정책, 확보 개수, 튜너 지급 가정, 표본 수.
- `material_scenarios`: 관측 재료량과 목표량, 수령 행동력, 표본 수.
- `assumptions`, `limitations`: 후보 재고·실측 버전·지급 참조·달력 시간 제외 등 적용 조건.

결과의 `waveplate_equivalent_days`는 소모 행동력/240이며 실제 접속·전투·후보 획득·해금 시간을 포함하지 않습니다. `exact_per_kept_echo`는 후보당 합격률 및 합격품 1개까지의 평균 자원 비용을 상태 전이로 계산합니다. 경험치는 합산 자원으로 처리합니다. `screen10`과 `screen15`는 해당 단계까지 유효 크리티컬이 없거나 목표가 불가능해지면 폐기합니다. 일반 튜닝만 지원하며 재구성·천장·계정별 실시간 서버 보정은 모델링하지 않습니다.
